1. Application Configuration config

The config { ... } block declares global application metadata, target SQL database dialect, authentication strategy, documentation, migration scripts, and object storage.

3. Field Decorators & Constraints decorators

Decorators attach validation, security rules, storage bindings, indexes, and lifecycle hooks directly to model fields and automatically propagate constraints to generated request DTOs.

Decorator Applies To Generated Spring Boot / JPA Effect
@id Field Marks field as Entity Primary Key (@Id in JPA).
@auto Long, Int, UUID Generates GenerationType.IDENTITY for integers or auto-generated UUIDs on persist.
@unique Field Adds unique constraint in database and generates findBy<Field> in repository.
@index Field or Model Creates a secondary B-tree database index on a single field (email: String @index) or composite model fields (@index([customer, status], name = "idx_custom")). Emits both Flyway SQL CREATE INDEX DDL and JPA @Table(indexes = { @Index(...) }).
@uniqueIndex Field or Model Creates a unique secondary or composite index (@uniqueIndex([orderNumber, customer])). Emits CREATE UNIQUE INDEX in Flyway DDL and @Index(..., unique = true) in JPA.
@password String Automatically enforces @NotBlank and @Size(min = 8, max = 100) on the Create<Model>Request DTO, hashes with BCrypt on registration/seeding, and masks from API responses (@JsonIgnore).
@email String Enforces valid RFC 5322 email syntax with Jakarta Bean Validation @Email on both JPA entities and request DTOs.
@positive Numeric Enforces value > 0 with Jakarta @Positive on entities and request DTOs. Ideal for prices, amounts, and quantities.
@min(n) / @max(n) Numeric Enforces minimum and maximum numeric thresholds with @Min(n) / @Max(n) on entities and request DTOs.
@length(n) String Enforces exact string length with @Size(min=n, max=n) on request DTOs and @Column(length=n) on entities.
@autoNow DateTime Auto-populates with LocalDateTime.now() upon entity insertion (@PrePersist). Automatically imports LocalDateTime.
@autoUpdate DateTime Auto-updates with current timestamp whenever entity is updated (@PreUpdate). Automatically imports LocalDateTime.
@text String Maps to SQL TEXT / large object column with JPA @Lob and columnDefinition = "TEXT".
@role Enum Designates the user role attribute for Spring Security role-based access control (RBAC). The field's default value (e.g. role: Role = CUSTOMER @role) consistently sets the project-wide default role across entities, registration, CustomUserDetailsService, and automated tests.
@rateLimit Endpoint or Route Enforces token-bucket rate limiting via Bucket4j (e.g. @rateLimit("10/minute") or @rateLimit(requests = 50, per = "1m")). Emits standard RFC response headers (X-Rate-Limit-Remaining, Retry-After) and HTTP 429 when throttled.
@relation(...) Relation field Declares JPA relationship mappings (oneToMany, manyToOne, oneToOne).
@file(maxSize, types, path) String Configures general file upload attribute: max file size (e.g. "10MB"), allowed MIME types (e.g. ["application/pdf"]), and folder path. Generates entity upload/download/delete endpoints only when endpoints and crud exist on the model.
@image(maxSize, types, path) String Configures image upload attribute with image-specific validation (defaults to JPEG, PNG, WebP) and thumbnail streaming. Generates media endpoints only when endpoints and crud exist on the model.

Single-Column & Composite Database Indexes (@index, @uniqueIndex)

Eliminate full table scans on high-cardinality filter columns, foreign keys, and multi-column lookups. Zenith supports inline single-column indexes and model-level composite indexes, compiling them into both Flyway DDL and JPA @Table(indexes = ...) annotations with automatic 63-character identifier truncation and reserved SQL keyword quoting:

model Order {
    id: UUID @id @auto
    orderNumber: String(length = 32) @unique
    status: OrderStatus = PENDING @index             // 1. Inline single-column index
    totalAmount: Decimal(precision = 12, scale = 2)
    createdAt: DateTime @autoNow

    relations {
        customer: Customer @relation(manyToOne)
    }

    // 2. Model-level composite index (resolves relation 'customer' -> 'customer_id')
    @index([customer, status])

    // 3. Composite index with explicit custom name
    @index([status, createdAt], name = "idx_orders_status_timeline")

    // 4. Composite unique index across multiple columns
    @uniqueIndex([orderNumber, customer])
}

// Emitted JPA Entity Annotation:
// @Table(name = "orders", indexes = {
//     @Index(name = "idx_orders_status", columnList = "status"),
//     @Index(name = "idx_orders_customer_id_status", columnList = "customer_id, status"),
//     @Index(name = "idx_orders_status_timeline", columnList = "status, created_at"),
//     @Index(name = "uidx_orders_order_number_customer_id", columnList = "order_number, customer_id", unique = true)
// })
💡 Placement Tip & Best Practice: Place model-level composite indexes (@index([...]) and @uniqueIndex([...])) below the relations { ... } block (or right before endpoints { ... }). Because composite indexes frequently reference foreign-key relations (such as customer in @index([customer, status])), declaring them after relations keeps your schema logical and avoids any ambiguity with inline field decorators on the preceding field line.

Declarative API Rate Limiting (@rateLimit & Token Bucket)

Shield transactional endpoints from automated brute-force attacks and volumetric denial of service. Zenith emits a high-performance RateLimitingFilter powered by Bucket4j, enforcing token-bucket capacity per authenticated user ID or client IP address:

model Checkout {
    id: UUID @id @auto
    amount: Decimal(12, 2)

    endpoints {
        // Option 1: Decorator syntax on custom routes
        @rateLimit(requests = 5, per = "1m")
        post "/pay" -> OrderResponse {
            action: {
                // Payment processing logic
            }
        }

        // Option 2: Shorthand string syntax
        @rateLimit("10/minute")
        post "/one-click" -> Void {
            action: { }
        }

        // Option 3: Route body property
        post "/verify" -> Void {
            rateLimit: "3/second"
            action: { }
        }

        // Option 4: Model-wide CRUD throttling
        crud {
            rateLimit: "60/minute"
            list: public
        }
    }
}

4. Enums & Role-Based Security security

Enums define discrete domain states or application roles. Designating a field with @role integrates directly with Spring Security 6, automatically establishing project-wide role consistency.

Default Role Resolution: The default value assigned to the @role attribute (e.g. role: Role = DEVELOPER @role) becomes the canonical default role throughout the generated application—assigned to new users on registration, populated in entity @PrePersist hooks, and evaluated in security test suites.

enum Role {
    ADMIN,
    MANAGER,
    DEVELOPER
}

enum TaskStatus {
    TODO,
    IN_PROGRESS,
    IN_REVIEW,
    DONE,
    CANCELLED
}

model UserEntity {
    id: UUID @id @auto
    email: String @email @unique
    password: String @password                   // Enforces @NotBlank & @Size(min=8, max=100) on Create DTO
    role: Role = DEVELOPER @role                 // Canonical default role assigned on register
    fullName: String(min = 2, max = 100)         // Validated on both entity & DTO
    avatar: String? @image(maxSize = "5MB", types = ["image/jpeg", "image/png"])
    createdAt: DateTime @autoNow                 // java.time.LocalDateTime auto-imported
}

6. CRUD & Custom Endpoints (API Security & RBAC) endpoints

The endpoints { ... } block declares standard REST controllers and custom domain routes. When auth: jwt is enabled, Zenith integrates seamlessly with Spring Security 6 and emits @PreAuthorize(...) annotations to strictly control public vs authenticated access and Role-Based Access Control (RBAC).

Zero-Config Security Defaults

If no explicit security flags are declared, Zenith follows standard enterprise conventions: read operations are public (@PreAuthorize("permitAll()")), while write operations require authentication (@PreAuthorize("isAuthenticated()")).

Security Control Options Matrix

⚠️ Architectural Rule — Never Return Raw Entity Models in REST Endpoints:
Auto-generated DTOs for any model <ModelName> always end with <ModelName>Response or Request (<ModelName>Response, Create<ModelName>Request, Update<ModelName>Request). You cannot return a raw JPA entity directly in a REST endpoint (e.g., post "/{id}/cancel" -> Order is invalid and caught immediately by the Zenith Studio compiler). Always use -> <ModelName>Response, -> List<<ModelName>Response>, a custom dto, or -> Void.

Comprehensive Example: Granular CRUD & Custom Endpoint Security

model Order {
    id: UUID @id @auto
    orderNumber: String(length = 20) @unique
    totalAmount: Decimal(precision = 12, scale = 2) @positive
    status: OrderStatus = PENDING
    createdAt: DateTime @autoNow

    relations {
        customer: Customer @relation(manyToOne)
    }

    endpoints {
        // Granular CRUD RBAC:
        // - Public can view and list orders
        // - Authenticated customers can place orders (POST)
        // - Staff (MANAGER/ADMIN) can update status (PUT)
        // - Only ADMIN can delete orders (DELETE)
        crud {
            paginate: true
            search: [orderNumber]
            filter: [status]
            sort: [createdAt, totalAmount]
            list: public
            get: public
            create: auth                      // Any authenticated user
            update: [MANAGER, ADMIN]          // Managers and Admins
            delete: [ADMIN]                   // Admins only
        }

        // 1. Public Custom Endpoint: Tracking without logging in
        get "/track/{orderNumber}" -> OrderResponse {
            public: true                      // @PreAuthorize("permitAll()")
            description: "Allows public package tracking by order number"
            query: orderNumber == orderNumber
        }

        // 2. User-Scoped Endpoint: My personal orders
        get "/my-orders" -> List<OrderResponse> {
            user: true                        // Automatically filters customer == currentUser
            description: "Returns orders placed by the authenticated user"
        }

        // 3. Custom DTO Return with Auto-Mapping & Domain Action
        post "/{id}/pay" -> OrderSummaryResponse {
            auth: true
            guard: status == OrderStatus.PENDING, "Only pending orders can be marked as paid"
            action: {
                status = OrderStatus.PAID
                create AuditLog {
                    action = "ORDER_PAYMENT_PROCESSED",
                    details = "Order " + entity.orderNumber + " marked PAID by " + currentUser.email
                }
                notify(entity.customer.email, "Your payment for order " + entity.orderNumber + " succeeded!")
            }
        }

        // 4. Role-Restricted State Transition with Domain Guard
        post "/{id}/ship" -> OrderResponse {
            auth: [LOGISTICS, ADMIN]          // @PreAuthorize("hasAnyRole('LOGISTICS', 'ADMIN')")
            description: "Dispatches the shipment"
            guard: status == OrderStatus.PAID, "Only paid orders can be shipped"
            action: {
                status = OrderStatus.SHIPPED
                notify(entity.customer, "Your order #" + entity.orderNumber + " has been shipped!")
            }
        }

        // 5. Combined Declarative Role & Domain Guard
        post "/{id}/cancel" -> Void {
            auth: true
            guard: role in [ADMIN, SUPPORT], "Only Support or Admin can cancel orders"
            guard: status != OrderStatus.DELIVERED, "Delivered orders cannot be cancelled"
            action: {
                status = OrderStatus.CANCELLED
                create AuditLog {
                    action = "ORDER_CANCELLED",
                    details = "Order " + entity.orderNumber + " cancelled by " + currentUser.email
                }
            }
        }
    }
}

7. Advanced Action Logic & Domain Operations actions

Transform Zenith into a full business logic framework. The action: { ... } block executes multi-entity domain mutations, updates related secondary models, instantiates secondary entities, logs audit trails, and triggers notifications with authenticated user context.

Supported Domain Operations

Operation Zenith Syntax Generated Spring Boot 3 Logic
Action Variable Binding var item = create Item { ... }
var target = update Model { ... }		 Binds persisted entity returned from repository.save() to a typed local variable in Java, enabling multi-entity chaining, ID capture, and transactional property propagation.
Primary Entity Mutation status = TaskStatus.DONE entity.setStatus(TaskStatus.DONE); followed by repository.save(entity);
Secondary Entity Update update Project { where: id == entity.project.id, completedTasks = entity.project.completedTasks + 1 } Injects ProjectRepository, fetches target entity by ID via findById(...), executes setters, and calls save().
Secondary Entity Creation create AuditLog { action = "TASK_DONE", details = "..." } Injects AuditLogRepository, instantiates new entity, populates fields, and calls save().
Date & Time Helpers now(), today(), daysFromNow(n), hoursFromNow(n), daysAgo(n) Translates to type-safe LocalDateTime.now().plusDays(n) or minusDays(n) with automatic imports. Dot notation like 3.daysFromNow is also supported.

Event & Notification Hook notify(entity.project.owner, "Message") Dispatches asynchronous domain notification to the target recipient.

Action Variable Binding (Multi-Entity Chaining)

Capture database-generated IDs, timestamps, and relations by binding create or update expressions to locally scoped variables with var:

// Example: Checkout workflow capturing generated invoice and shipment
post "/checkout" -> OrderSummaryResponse {
    auth: true
    action: {
        // 1. Create invoice and bind to variable 'inv'
        var inv = create Invoice {
            orderNumber = "ORD-" + randomUUID(),
            totalAmount = body.totalAmount,
            status = InvoiceStatus.PAID
        }

        // 2. Reference inv.id and inv.totalAmount in subsequent creation
        var ship = create Shipment {
            invoiceId = inv.id,
            trackingNumber = "TRK-" + randomUUID(),
            status = ShipmentStatus.PENDING
        }

        // 3. Update primary entity with invoice & shipment metadata
        status = OrderStatus.FULFILLED
        invoiceNumber = inv.orderNumber
        trackingId = ship.id
    }
}

How to Use update for Secondary Entities

When executing an action on a primary model (e.g. completing a Task or fulfilling an Order), you frequently need to mutate a secondary model (e.g. updating parent Project counters, decrementing Product inventory, or adjusting account balances). The update Model { ... } block handles this declaratively with automatic repository injection and null-safe persistence:

// Example 1: Updating parent Project stats when a Task is finished
update Project {
    where: id == entity.project.id
    completedTasks = entity.project.completedTasks + 1
    lastActivityAt = DateTime.now
}

// Example 2: Updating inventory stock when an Order is fulfilled
update Product {
    where: id == entity.product.id
    stock = entity.product.stock - entity.quantity
}

Complete Example: Mutations, Updates, Secondary Creation & Notifications

post "/{id}/complete" -> Void {
    auth: true

    action: {
        // 1. Mutate primary entity

        // 4. Event / Notification hook
        notify(entity.project.owner, "Task completed: " + entity.title)
    }
}

Strict Semantic Analysis & Compiler Error Reporting

The Zenith transpiler enforces strict compile-time verification across all actions and jobs. Unsupported statements, invalid method calls, or referencing unknown target fields (e.g. update Model { unknownProp = ... }) immediately halt compilation with clear diagnostic messages. Zenith guarantees that invalid expressions never silently pass through or produce non-compiling Java output.

8. Data Transfer Objects & Endpoint Auto-Mapping dto

Define custom request and response payloads decoupled from JPA database models with strict typing and optionality. DTOs compile directly to Java 17 records and TypeScript client interfaces.

⚠️ Mandatory DTO Naming & Entity Protection: For every model <ModelName>, Zenith automatically generates <ModelName>Response, Create<ModelName>Request, and Update<ModelName>Request. Model DTO names always end with Response or Request. Returning or accepting a raw model entity in an endpoint (e.g. -> CustomerOrder or (body: CustomerOrder)) is strictly forbidden and raises a compile-time error in Zenith Studio. 
dto AssignTaskRequest {
    assigneeId: UUID
    comment: String?
    priority: Priority?
}

dto OrderSummaryResponse {
    id: UUID
    orderNumber: String
    totalAmount: Decimal
    status: OrderStatus
    customerId: UUID?                 // Automatically mapped from entity.customer.id
}

Custom DTO Return Types on Endpoints & Automatic Field Mapping

When an endpoint declares a custom DTO return type (e.g. post "/{id}/pay" -> OrderSummaryResponse or get "/summaries" -> List<OrderSummaryResponse>), Zenith automatically synthesizes a specialized conversion method in {Model}Mapper.java without requiring boilerplate mapping code:

Mapping Rule Behavior Transpiled Java Output
Coincident Field Matching Directly copies attributes present in both the model and the DTO with compatible types. entity.getOrderNumber() → orderNumber
Relational Foreign Key Resolution If a DTO field is named {relation}Id (e.g. customerId: UUID) and the model has a relation customer: Customer, Zenith automatically extracts the relation ID with null-safety. entity.getCustomer() != null ? entity.getCustomer().getId() : null
Unmatched / Computed Fields DTO fields not present on the model receive safe typed defaults (0, "", null) or can be populated via custom query logic. totalItems: 0 / summary: null
Service & Controller Wiring Service interface and implementation return the custom DTO via mapper.to{DtoName}(entity), and Spring REST controllers emit ResponseEntity<{DtoName}>. return orderMapper.toOrderSummaryResponse(entity);

Option A: Explicit return DTO { ... } in the Action Block

Allow explicit DTO return construction inside the action: { ... } block for customized computed fields, aggregations, and authenticated user context:

// Emits Spring @Component with @Scheduled and @Transactional:
@Component
@ConditionalOnProperty(name = "jobs.archive-old-tasks.enabled", havingValue = "true", matchIfMissing = true)
public class ArchiveOldTasksJob {
    private final TaskRepository taskRepository;

    @Scheduled(cron = "${jobs.archive-old-tasks.cron:0 0 2 * * ?}")
    @Transactional
    public void execute() {
        taskRepository.findAll().stream()
            .filter(target -> (target.getStatus() != null && "DONE".equalsIgnoreCase(target.getStatus().name()))
                           && (target.getUpdatedAt() != null && target.getUpdatedAt().isBefore(LocalDateTime.now().minusDays(30))))
            .forEach(target -> {
                target.setStatus(TaskStatus.ARCHIVED);
                taskRepository.save(target);
            });
    }
}

Bulk Stream Filter Transpilation Rules

When an update Model { ... } statement inside a job action contains non-ID or multi-attribute criteria (e.g., where: status == DONE and updatedAt < daysAgo(30)), the transpiler applies intelligent pipeline transformations:

  • Repository Stream Pipeline: Compiles to repository.findAll().stream().filter(...).forEach(...).
  • Temporal Operator Mapping: Converts all date comparison operators (< → .isBefore(...), <= → (!.isAfter(...)), > → .isAfter(...), >= → (!.isBefore(...)), == → .isEqual(...), != → (!.isEqual(...))) with strict null-safety.
  • Automatic Date Imports: Detects temporal predicates and guarantees automatic injection of java.time.LocalDateTime and java.time.LocalDate imports.
  • Enum Name & Value Matching: Normalizes enum literals into type-safe comparisons (e.g. target.getStatus() != null && "DONE".equalsIgnoreCase(target.getStatus().name())).
  • Transactional Batch Persistence: Executes all field mutations on matched entities and saves each back to the database within a transactional boundary (@Transactional).
