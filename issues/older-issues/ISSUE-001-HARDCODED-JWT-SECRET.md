# Issue Report: ISSUE-001 — Hardcoded JWT Secret Key & Missing Config Keys in Zenith DSL

- **Issue ID**: `ISSUE-001`
- **Discovery Date**: `2026-11-07`
- **Classification**: Security Vulnerability / Compiler Feature Gap (CWE-798: Use of Hard-coded Credentials)
- **Severity**: `P1 (High)`
- **Status**: `FIXED`
- **Tested**: `TESTED` *(Verified via unit compilation, parser/semantic validation test matrix, and Spring code emission)*
- **Affected Subsystems**:
  - `dev.zenith.parser.Parser` (Grammar & `ALLOWED_CONFIG_KEYS`)
  - `dev.zenith.analyzer.SemanticAnalyzer` (Config validation)
  - `dev.zenith.ast.AppConfig`
  - `dev.zenith.generator.SecurityGenerator`
  - `dev.zenith.generator.PropertiesGenerator`
  - `generated-app/src/main/java/com/example/app/security/JwtService.java`
  - `generated-app/src/main/resources/application.yml`

---

## 1. Problem Description & Root Cause Breakdown

In `generated-app` (and all Spring Boot applications generated by Zenith when `auth: true` is enabled), the cryptographic JWT signing key is baked directly into `JwtService.java` as a `private static final String`:

```java
// File: generated-app/src/main/java/com/example/app/security/JwtService.java:18-19
@Service
public class JwtService {

    private static final String SECRET_STRING = "404E635266556A586E3272357538782F413F4428472B4B6250645367566B5970";
    private static final long EXPIRATION_MS = 86400000L;
```

### The Architectural Root Cause: Two Interconnected Gaps

The issue is **not just in the generated Java file**, but in how the Zenith compiler handles configuration:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ GAP 1: In the Zenith Language (Parser & Semantic Analyzer)                             │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ The Zenith parser rejects `jwtSecret` and `jwtExpiration` in the `config { ... }` block│
│ because `Parser.ALLOWED_CONFIG_KEYS` only allows:                                      │
│   ["app", "package", "basepath", "port", "database", "auth",                           │
│    "swagger", "flyway", "storage", "storagebucket", "usermodel"]                       │
│                                                                                        │
│ If a user writes:                                                                      │
│   config {                                                                             │
│       jwtSecret: "my-custom-key"                                                       │
│       jwtExpiration: 3600000                                                           │
│   }                                                                                    │
│ The parser throws: ParseException: "Invalid configuration key 'jwtSecret'".           │
└────────────────────────────────────────────────────────────────────────────────────────┘
                                           │
                                           ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ GAP 2: In the Generator Implementation                                                 │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ Although `AppConfig.java` already has methods ready:                                   │
│   - `getJwtSecret()` (falls back to default "404E635266556A586E3272...")               │
│   - `getJwtExpirationMs()` (falls back to default 86400000L)                           │
│                                                                                        │
│ The generators currently output static strings:                                        │
│   1. `SecurityGenerator.java`: Bakes `private static final String SECRET_STRING = ...` │
│   2. `PropertiesGenerator.java`: Emits `jwt.secret: "..."` literal into yml            │
│      without environment variable fallback `${JWT_SECRET:...}`.                        │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

---

## 2. Why This Is a Critical Defect

1. **Language Inflexibility**: Developers cannot customize their JWT secret or token expiration from within `.zen` schemas because the language parser forbids the keys.
2. **Hardcoded Credentials Leak**: The generated Spring Boot code hardcodes `SECRET_STRING` into bytecode and Git source control.
3. **No Environment Variable Overrides**: Cloud deployments (Docker, Kubernetes, AWS ECS) cannot inject `JWT_SECRET` dynamically at startup without recompiling the Java code.
4. **Token Forgery**: Any user with read access to the repo can forge administrative JWT tokens using the public static string.

---

## 3. Required End-to-End Solution Specification

The remediation must be executed across **4 distinct layers** of Zenith:

### Layer 1: Parser Grammar & Allowed Config Keys (`Parser.java`)

1. **Add Keys to `ALLOWED_CONFIG_KEYS`**:
   In `src/main/java/dev/zenith/parser/Parser.java`:
   ```java
   private static final Set<String> ALLOWED_CONFIG_KEYS = Set.of(
           "app", "package", "basepath", "port", "database", "auth",
           "swagger", "flyway", "storage", "storagebucket", "usermodel",
           "jwtsecret", "jwtexpiration"
   );
   ```

2. **Validate Syntax in `parseConfig()`**:
   - `jwtsecret`: Must be a non-empty string. If hex/Base64, must be at least 256 bits (32 bytes / 64 hex chars) for HMAC-SHA256 compliance.
   - `jwtexpiration`: Must be a positive long integer (in milliseconds) or duration format.

---

### Layer 2: Semantic Analyzer (`SemanticAnalyzer.java`)

Add semantic validation in `SemanticAnalyzer.java`:
- If `jwtSecret` or `jwtExpiration` is declared in `config { ... }` while `auth` is set to `none` or `false`, emit an `AnalysisException` warning or error:
  `"Configuration 'jwtSecret' is only valid when authentication is enabled (auth: jwt)."`
- Validate that `jwtSecret` length meets the minimum cryptographic strength for `io.jsonwebtoken.security.Keys.hmacShaKeyFor` (minimum 256 bits).

---

### Layer 3: Compiler Generators (`SecurityGenerator.java` & `PropertiesGenerator.java`)

#### A. `PropertiesGenerator.java`
Update lines 95-98 to emit externalized environment variable syntax into `application.yml`:
```yaml
jwt:
  secret: ${JWT_SECRET:"<file.getConfig().getJwtSecret()>"}
  expiration: ${JWT_EXPIRATION_MS:<file.getConfig().getJwtExpirationMs()>}
```
*Result*: Local dev works automatically with the default, while production seamlessly overrides via `export JWT_SECRET=...`.

#### B. `SecurityGenerator.java`
Update `generateJwtService(...)` to import Spring's `@Value` and inject the configuration dynamically instead of using `static final` constants:
```java
package <basePkg>.security;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Service;

import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.util.Date;
import java.util.HashMap;
import java.util.Map;
import java.util.function.Function;

@Service
public class JwtService {

    @Value("${jwt.secret}")
    private String secretString;

    @Value("${jwt.expiration:86400000}")
    private long expirationMs;

    private SecretKey getSigningKey() {
        return Keys.hmacShaKeyFor(secretString.getBytes(StandardCharsets.UTF_8));
    }
    // ...
```
